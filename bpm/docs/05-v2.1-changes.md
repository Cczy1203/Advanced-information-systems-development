# v2.1 - keeping every scored element while thinning the picture

> **Historical.** This document records the v2.1 step. The numbers in it
> (canvas 7,496 x 14,034, crossings 197, 4 clipped lines) describe v2.1 as it
> stood at that review. The shipped third release supersedes them: 123
> crossings, 0 clipped lines, canvas 7,496 x 14,176. See
> `06-diagram-engineering.md` and `03-test-record.md` section I.

v2.0 worked, deployed and ran, but the canvas was hard to read: 66 dashed message
flows ran the full height of an 8,928 px wide drawing and the end of almost every
branch had its own circle. v2.1 attacks the density and nothing else. Not one
scored element was removed, and the two processes still run end to end.

Everything in this document was produced by parsing the two files, not from
memory. `tools/verify_preservation.py` re-runs the whole checklist.

---

## 1. What changed

### Message flows are drawn once per pair of pools

66 dashed lines became 31. Camunda 8 never reads a message flow at run time - the
hand-off happens because the throwing event carries
`<zeebe:taskDefinition type="publish-message">` and the catching side is
subscribed to that message name. The line is documentation. So where several
hand-offs ran between the same two pools, the drawing now keeps one
representative line and the rest are gone from the diagram only.

The thinning prefers to keep exception hand-offs, so the lines that carry the
interesting story survive.

Measured effect: **421,424 px of dashed line down to 174,820 px, a 59% cut.**

### Routine end events are merged

Sixty end events became 32. Several branches in the same lane finished a few rows
apart and each drew its own circle. Ends that sit within three rows of each other
in the same lane now share one.

Exception ends are never merged. `_exception_ends()` walks forward from every
boundary event and marks those ends as distinct, so "referral rejected" and
"letter escalated" still terminate visibly on their own.

### Lanes were consolidated

20 lanes became 14. Lanes that only ever held one or two steps were folded into a
neighbouring lane of the same pool. Pool names and the fifteen participants are
untouched.

## 4. What v2.1 did not achieve

The reduction targets were flow nodes ~200, events under 80, message flows 25-30.
Message flows landed at 31, inside the band. The other two did not, and the
reason is arithmetic rather than effort.

An event count under 80 is not reachable while every hand-off is kept. The floor
is:

| unavoidable events | count |
|---|---:|
| start events (one per incoming message name) | 43 |
| message throw events (one per hand-off) | 68 |
| message catch events | 10 |
| boundary events | 18 |
| end events (exception ends cannot be merged) | ~24 |
| **floor** | **~163** |

v2.1 sits at 171, close to that floor. Getting under 80 means deleting either the
message starts, the hand-off throws, or the exception ends - all three are on the
preservation list. Your own rule applies: **where a reduction conflicts with
preservation, preservation wins.**

### Start events: still 43, target was 2 per pool

This is the clear miss. A Camunda 8 message start event subscribes to one message
name, so 43 distinct message names need 43 start events. Collapsing them to two
per pool means renaming the protocol: every thrower targeting a pool would publish
`Msg_<pool>` plus a `requestType` discriminator, and each pool would gain a
dispatch gateway behind a single start event.

That is a real change to the message contract of a model that currently deploys
and runs clean, so it was not made in this pass. It is the single highest-value
follow-up: it would take start events from 43 to about 18 and cut 25 events.

### Crossings went up, from 147 to 197

This is the cost of merging the end events, measured by A/B rather than guessed:

| variant | nodes | end events | crossings |
|---|---:|---:|---:|
| v2.0 baseline | 329 | 60 | 147 |
| pool-wide end merge | 281 | 27 | 208 |
| lane-scoped end merge (v2.1) | 301 | 32 | 197 |

Merging makes several distant branches converge on one circle, so their lines now
cross other branches on the way. The lane-scoped variant was chosen as the better
of the two, but the trade is real and it is a step backwards on the measure the
brief calls the biggest score lever.

If crossings matter more than the 28 circles, setting `_merge_end_events` aside
returns the drawing to 147 crossings and 60 end events with nothing else changed.

### Sub-process steps are in the file but the boxes stay closed

The three embedded sub-processes (`Call handling contact`, `Secretaries dispatch`,
`Pathway report`) each hold 4-6 steps. They were briefly drawn open with full
diagram interchange for every child. That was reverted, because a box wide enough
to show six steps spans about five columns of a 165 px grid and drags the
neighbouring runs straight through it:

| | closed (v2.1) | open (tried, reverted) |
|---|---:|---:|
| lines through an unrelated shape | 4 | 21 |
| sequence flow overlaps | 0 | 3 |
| drawn elements | 339 | 681 |

The brief requires lines not to pass through shapes, and the point of v2.1 was
less density. Keeping the boxes closed wins on both. The steps are all still in
the XML, they still execute, and each sub-process carries a `<bpmn:documentation>`
note describing what it contains, so nothing is hidden from a reader of the file.
Flip `V2Builder.EXPAND_SUBPROCESSES` to `True` to see the open version.

**This is a deliberate trade and it is visible in Camunda Modeler.** The status
bar reads **0 errors, 30 warnings**, and running the same lint rule set the
Modeler uses shows the 30 are all one rule:

```
  40 fake-join              Incoming flows do not join
  30 no-bpmndi              Element is missing bpmndi      <-- the 30 in the status bar
   7 label-required         Element is missing label/name
   6 no-overlapping-elements
   3 no-inclusive-gateway   Element type <bpmn:InclusiveGateway> is discouraged
   2 no-implicit-start
```

The 30 `no-bpmndi` warnings are exactly the collapsed sub-processes' hidden
steps. Drawing them open removes all 30 and replaces them with overlap warnings
and 17 lines through a shape, which is the worse outcome for a diagram whose
whole purpose is to be read. **Nothing is reported as an error.**

The other categories are pre-existing and mostly deliberate: `fake-join` warns
where several flows merge into a task without a gateway, which is normal BPMN and
is how the exception paths rejoin the main line; `no-inclusive-gateway` is a
style preference and the inclusive gateway is there on purpose (see
`04-modelling-decisions.md`); `no-implicit-start` is the compensation handler,
which by definition has no incoming flow.

### Four lines still clip a boundary event

Down from an earlier count but not zero. All four are a sequence flow running
along the same y as a boundary event that sits on its host's bottom edge:

```
Flow_012          passes through SEC_Bnd_PackIncomplete
Flow_063          passes through CON_Bnd_LetterReminder
Flow_226          passes through TRT_Bnd_ConfirmationLost
MessageFlow_30    passes through CON_Bnd_LetterOverdue
```

Out of 311 sequence flows and 31 message flows. These are the 6
`no-overlapping-elements` warnings. Not fixed in this pass.
